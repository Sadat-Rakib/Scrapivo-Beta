# Browser lifecycle trace (Task 3)

Harness: `browser-trace.mts` (local no-persist guard enforced). Raw traces: `BROWSER_TRACE_{FOUNDERS,BUSINESSES}_{SMOKE,PRODUCT}.json`; page captures in `captures/`. All four runs were headless, matching the earlier checkpoint smokes.

## Runtime verdict: RUNTIME_OK
Chromium launched, navigated, and read substantial text (up to the 18,000-char cap) on every opened page. Navigation and reads did not cause the loss. Evidence is lost earlier, at search-result selection, and again at extraction.

## First failing boundary: SERP → organic result links
1. **Wrong links are opened.** `PlaywrightBrowserAdapter` has no `extractLinks`. `search()` therefore falls back to every anchor on the Bing page. The first "results" opened were Bing chrome: Microsoft Support accessibility, Bing Image Creator, Copilot, a Wikipedia sidebar link, and zhihu. `destination()` unwraps Bing `ck/a` and DDG `uddg` redirects but skips the engine-host filter on the decoded target, so engine-owned pages pass.
2. **The DuckDuckGo bot challenge is missed.** Headless Chromium gets DDG's "Unfortunately, bots use DuckDuckGo too" page (verified with `tools/serp-probe.mts`). The captcha check runs only when `extractLinks` exists, so the challenge showed up as an empty SERP rather than BLOCKED. Headless Bing also returns degraded results: "Best Buy" for "best restaurants in Calgary Alberta". Headed Chromium, the local product default, gets real DDG and Bing results.
3. **Structured search and SERP budget.** SearXNG (`127.0.0.1:8888`) was unreachable. It was re-probed for every query, adding a 4-second probe each time. The browser SERP fallback allows only 2 searches per run, so later discovery and candidate-research queries get nothing.

## Second boundary: extraction
- Business pages have no deterministic extractor. The LLM returned `{"entities":[]}` for a restaurantji list page. That page was for Airdrie, not Calgary, because of the degraded headless SERP.
- JSON-LD is read from the first `ld+json` script only (`locator().first()`), so ItemList and LocalBusiness data in later blocks is never seen.

## Understanding blocker found on the product path (fixed)
The provider frame for "Restaurants in Calgary, Alberta with official websites" kept `has_asset` but dropped its object. The canonical decision then asked a relation question even with `force`, so no search ran. The fix in `to-search-spec.ts` recovers the object only when the deterministic parse observed the same relation. Test: `src/lib/understanding/llm-frame-repairs.test.ts`. After the fix the business product path returned 10 qualified rows from structured sources. Browser research was not needed, so that query is not a browser-required gate query.
