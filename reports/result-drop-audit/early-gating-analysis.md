# Early-gating analysis

The hypothesis is **partly true**. Partial candidates exist in browser memory and the DB incomplete pool, but only selected seeds get browser work. After browser return, a live row must pass `rowSatisfiesSpec` **before** the general enrichment pass; incomplete live rows receive only the capped site-contact pass and then remain pending.

| Question | Current code answer |
|---|---|
| 1. First live/browser fields | `defaultWeb` creates title/detail/source URL, provisional ID, `entity_resolved:false` (`live-gapfill.ts:198-250`). Browser `remember` needs a title and compatible kind; its initial-seed filter also needs source/destination URL or resolved location (`browser-live.server.ts:~755`). OSM/index rows may start resolved with name/category/location and null site. |
| 2. Complete before deeper enrichment? | **No for DB**: core merges complete and incomplete DB rows for `enrichCandidatesForSpec` (`spec-search.functions.ts:~1680`). **Sometimes for live**: browser research sees partial seeds, but post-live query-aware enrichment receives only `completeRows` (`:~1730-1850`). |
| 3. `rowSatisfiesSpec` before research? | **Yes for no-site seed selection** (`live-gapfill.ts:~695`), and on DB rows before core enrichment (`spec-search.functions.ts:~1630`). Non-no-site web seeds are taken from first six without this check; live rows are checked again after browser return. |
| 4. `applyWhyMatchGate` before enrichment? | It is used on already `completeRows` to calculate `qualifiedDbCount` and decide whether live discovery is needed (`spec-search.functions.ts:~1690`). It does **not** remove those DB rows there. Final call after enrichment does remove nonqualified rows. |
| 5. `applyQualificationGate` before enrichment? | Indirectly for the DB live-decision count and repeatedly in browser `refresh` (`browser-live.server.ts:441`). The destructive core application is after enrichment (`spec-search.functions.ts:~1890`). |
| 6. `isVerified` and seeds? | `runLiveGapfill` counts verified initial candidates to decide `shouldBrowse`; browser `refresh` also uses it for verified status/stopping. It does not itself create seeds; seed filters/caps do (`live-gapfill.ts:~690-735`). |
| 7. Can missing fields survive? | Email/phone: yes when not explicitly required, subject to entity completeness needing *some* channel/site. Website: yes for no-site and partial research; other company/business rows need site or contact to be complete. Profile: person can use email/phone instead, but browser may still seek profile. Signal/evidence: yes unless `signal_required` or no-site/topic claim. Why-match: may be derived after qualification. Role/company relation: provisional person can be researched, but final person gate rejects unproved relationship. |
| 8. Query versus global fields | `canonical-contract.ts:168` always requires stable entity ID/type/name; location only when stated; phone/email only under its explicit requirement patterns or flags; claim evidence when `signal_required`. `completeness.ts:29` separately imposes global contact/site alternatives by entity. Person gates require a supported current relationship for relevant person Specs. |
| 9. Partial versus invalid | Yes in browser memory: `researchStatus` maps repairable failures to `researching`/`exhausted`, hard type/location contradiction to `rejected` (`browser-research.ts:48`). Core retains `incompleteRows` separately, but final output admits only complete qualified rows. |
| 10. Early incomplete storage | Core DB and live `incompleteRows`; browser candidate memory retains incomplete rows until return. Core reports `pendingEnrichment`; it does not deliver that pool. |
| 11. Enrichment scope | Initial DB query-aware enrichment receives merged complete **and incomplete** DB rows. Post-live query-aware enrichment receives **only complete** rows. Incomplete live rows get the limited `enrichIncompleteRows` contact-site pass first. |
| 12. Browser scope | No-site: structured-absence, provenance-bearing Spec matches, ranked and capped at 15–20. Other: first six initial candidates; browser then ranks at most three provisional source pages and researches bounded resolved candidates (`live-gapfill.ts:~695`; `browser-live.server.ts:~755-825`). Not all useful partial candidates are visited. |
| 13. Contact data when unasked? | The theorem does **not** globally require email/phone. `completeness.ts` still requires a reachable channel **or** site for person/company/business unless no-site opportunity applies. C's “public contact details” triggers browser contact need by raw-query regex, but `queryRequiredFields` does not make contact URL/email/phone a final theorem requirement. |
| 14. Signal/why-match globally? | Signal proof is required only when `signal_required`, with separate explicit no-site and content-topic gates (`qualify.ts:130-164`). `applyWhyMatchGate` derives a directory why-match for non-signal qualified rows; a missing why-match alone is not the primary theorem rejection. |
| 15. Qualification before enrichment complete? | Yes in browser `refresh` and DB live-decision count. Those evaluations normally guide research/live discovery, not final drop. Final qualification after enrichment can reject if a needed field/proof was never obtained. |
| 16. Does enrichment discard? | `enrichIncompleteRows` returns unchanged rows on ordinary failure but places them in `stillIncomplete`; `enrichCandidatesForSpec` pushes every row even if unresolved, no plan, or adapter failure. The **core's later selection** excludes incomplete leftovers. Abort can end the entire run. |
| 17. Circular dependency? | **Yes, a conditional cycle for live company/business candidates:** global completeness asks for contact/site (`completeness.ts:29`); `enrichIncompleteRows` can harvest contacts only from a validated entity site (`enrich-incomplete.ts:27,46`); the post-live query-aware enrichment pass takes only complete rows (`spec-search.functions.ts:~1850`). If browser research fails to resolve the site/contact, the candidate remains pending and cannot enter that main pass. There is also a role/industry prefilter (`rowSatisfiesSpec`) before any post-live enrichment that could supply missing fit fields. |

For A, this cycle is not the observed final boundary: indexed plumbers already had public phones and were complete enough to reach browser research. Their absence claim lacked completed exact-name verification in the latest run.
