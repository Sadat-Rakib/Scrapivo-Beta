# Enrichment map

There are two different enrichment mechanisms in the core, plus browser research before live rows enter it.

| Step; file/function | Eligibility and input | Output fields/claims | Failure behavior |
|---|---|---|---|
| Browser needs `browser-research.ts:computeResearchNeeds` | Browser memory row plus current `qualifyLead` decision; requests identity, person role/company, stated industry/location, destination, contact, topic/signal, or no-site proof | A list of next research needs | Hard type/location mismatch yields no needs; row can become rejected/exhausted, but memory retains it. |
| Browser action `browser-live.server.ts:research` | Initial selected seeds or newly extracted entities; bounded attempts, queries, pages, and run time | Resolved fields, destination URLs, `contact_page_url`, field provenance, `no_website_verification.exact_queries`, extracted evidence | Blocked/thin/error pages return null. Candidate stays partial; timeout returns memory unless outer signal cancels, which returns `SEARCH_CANCELLED`. |
| DB/live first completeness `spec-search.functions.ts:sanitizeSpecRow` + `completeness.ts:missingRequiredFields` | Coarse Spec-matched row | `complete`, `missingFields`, normalized URL semantics | Missing contact/site creates incomplete pool; no immediate deletion. |
| Incomplete contact pass `enrich-incomplete.ts:enrichIncompleteRows` | First `cap` incomplete rows; `contactSiteUrl` requires an entity site, excludes article/directory/profile | Public email/phone from `discoverContacts`, if observed | Failure returns original row. Complete and still-incomplete are separate outputs. Recheck omits `opportunity`; no-site rows without contact can remain incomplete. |
| Query requirements `enrichment-plan.ts:deriveEnrichmentRequirements` | Spec criteria and current row | Blocking/when-available/optional missing fields; no-site forbids URL/website and requests no-site claim | Does not modify row. |
| Plan `enrichment-plan.ts:buildEnrichmentPlan` | Missing nonoptional fields, provider catalog, contact/paid/step budget | Free-first ordered steps; skipped reasons | No adapter/coverage/budget means no step; row retained. Identity and claim-evidence cannot be filled by contact APIs. |
| No-site claim `enrichment-run.ts:defaultEnrichmentAdapters` | Resolved candidate, structured source URL/absence, two distinct exact queries, no official site | Subject-bound structural `no_website` claim, confidence 0.7 | Returns `has_website_cannot_verify_absence` or `website_status_requires_structured_and_exact_web_checks`; row retained without claim. |
| Contact harvest `enrichment-run.ts:defaultEnrichmentAdapters` | Requested/missing email/phone/url and validated entity site; no-site URL enrichment forbidden | Observed email/phone with provenance | No site → `no_validated_site_to_harvest`; error → empty patch; no invented contacts. |
| Other adapters `enrichment-run.ts:defaultEnrichmentAdapters` | Salary text or already-known registry location | Salary/location patch when supported | Empty patch if unsupported. Paid calls disabled in core. |
| Patch merge `enrichment-merge.ts:mergeEnrichmentIntoRow` | Existing row + adapter patch/claim, allowed fields and subject ID | Row with permitted fields, field provenance, evidence | Invalid/unbound/forbidden patches are ignored; prior row survives. |
| Single candidate `enrichment-run.ts:enrichCandidateForSpec` | Resolved candidate with plan | Merged row and diagnostics | Adapter absent/unavailable/throws: diagnostic and continue. Cancellation propagates. |
| Batch `enrichment-run.ts:enrichCandidatesForSpec` | All merged DB rows before live; later only complete live/DB rows not already enriched. Max 8 contact candidates, 20-second contact budget, no paid calls | One output row per input row, plus diagnostics | Unresolved/no need/error rows are pushed unchanged. |
| Final qualification `live-gapfill.ts:applyWhyMatchGate` → `qualify.ts:qualifyLead` | Only core `completeRows` after post-live enrichment | Qualified row, score, why-match; nonqualified omitted | No further enrichment after this point. |

**Missing email/phone/signal:** the adapters retain the candidate with null fields. The final theorem rejects email/phone only if `queryRequiredFields` marks them required. Signal proof is required when `signal_required`; no-site and topic requests have their own claim gates. Separately, global completeness can keep a row out of final output when it has no contact *and* no site (except no-site opportunity).

**Partial merge back:** DB rows: `known = mergeDuplicateCandidates([...completeRows, ...incompleteRows])`, `enrichCandidatesForSpec(known)`, then `checked = enriched.rows.map(sanitizeSpecRow)` and split again (`spec-search.functions.ts:~1680`). Live rows: `runLiveGapfill` merges source/browser rows, core sanitizes and Spec-filters them, runs the capped incomplete pass, merges `completeRows`, and runs query-aware enrichment on complete rows not in `enrichedDbKeys` (`:~1730-1850`). Thus an adapter's partial success is retained **if its row remains in the corresponding pool**; incomplete live leftovers do not reach final qualification.
